# 实机部署

## Nova2 V4 协议适配（本地分支 `feature-nova2-v4-protocol`）

此分支从 `feature` 创建，机械臂驱动按越疆公开 V4.6.5 TCP/IP 接口适配。目标设备固件为 `v4.6.5.0-Force-beta6`；该 beta 固件尚未进行真机验收。下文记录的 2026-09-09 实机命令和结果属于升级前环境，不能视为本分支的实机验证。

- 机器人控制机连接 Nova2 的 `29999` 端口，所有 Dashboard、关节运动 ServoJ 和即时 DO 命令共用该连接。此分支不连接 V3 的 `30003` 运动端口；夹爪仍使用原串口，RealSense 相机仍使用原 USB 链路。`30004` 是 V4 实时反馈端口，本项目当前仍通过 `29999` 的 `GetAngle()` 读取六关节角度。
- 启动前确认机器人处于可请求 TCP 控制的状态。驱动依次执行 `RequestControl()`、`EnableRobot()`、`SpeedFactor(...)`、`AccJ(...)`、`VelJ(...)`、`SetTool(1,...)`、`Tool(1)`、`StopDrag()` 和 `GetAngle()`。V4 关节速度命令是 `VelJ`，不是 V3 的 `SpeedJ`；上层构造参数 `speed_j` 保持兼容。控制模式切换的状态限制以[越疆 V4 SDK](https://github.com/Dobot-Arm/TCP-IP-Python-V4)为准。
- `ServoJ` 使用 `t=0.030,aheadtime=50.0,gain=500.0`，驱动按 `t` 限制连续发送间隔，避免复位或插值循环瞬间堆积命令。回复成功表示命令已接收，不表示机械臂已到位。ServoJ 不受 `SpeedFactor` 或 `VelJ` 比例限制，低速验收必须对目标点的角度变化和时间做速度规划，不能只调低全局速度。依据为官方 [运动接口](https://github.com/Dobot-Arm/TCP-IP-Python-V4/blob/feature/v4-optimization/dobot_sdk/api/motion.py)及[控制接口](https://github.com/Dobot-Arm/TCP-IP-Python-V4/blob/feature/v4-optimization/dobot_sdk/api/robot_control.py)；公开仓库会更新，不能等同于 Force-beta6 专版验证。
- 命令拒绝、回复超时、连接中断或无效关节数据都会阻止继续下发动作，故障后需要重新创建驱动。回复按分号收齐，并限制整次收包时长；超时或帧损坏后不复用连接。第一条动作也相对连接时读取的实际关节状态检查跳变。双臂任一侧连接、关节读取或动作发送失败会清理两侧连接。
- 退出时先尝试 `Stop()` 清空运动队列，再按配置 `DisableRobot()`，最后释放相机和串口；保留力矩使能时仍发送 `Stop()`。若 TCP 已断开，停止和下使能无法确认，日志会明确记录，不能把关闭本地连接当作机械臂已经停止。
- 单右臂 7 维、双臂 14 维、同步/异步 RTC 和语音入口的命令行及模型接口沿用下文说明。机器人侧和服务端应使用同一次代码交付，且 checkpoint、配置和 norm stats 对应。

真机可用后按以下顺序验收，并记录每步的固件标识、命令回复和日志：

1. 使用底层 `DobotConnection` 仅连接 `29999` 并读取 `GetAngle()`，核对六关节角度、顺序和弧度转换；不要调用会自动使能和初始化夹爪的 `DobotXTrainer.connect()` 来做只读验收。
2. 核对 TCP 控制权、使能、速度、工具偏移及退出拖拽模式的回复；确认退出时停止运动队列并按配置下使能。
3. 在清空工作空间并准备急停后，发送低速、小幅、单关节 ServoJ，核对目标与实测方向和变化量，再验收夹爪与 DO。
4. 依次验收单右臂同步、单右臂异步 RTC、语音、双臂同步和双臂异步 RTC。每个入口检查图像键、动作维度、动作跳变限制和故障退出。

模拟 TCP 回复与回归测试通过只能证明代码按公开 V4 接口工作；`v4.6.5.0-Force-beta6` 真机兼容性须以上述现场结果为准。

### 1.3 FFmpeg 与 PyAV 依赖问题

FFmpeg 和 PyAV 是两层不同的依赖：

- `ffmpeg` 是系统命令，缺失时通常表现为找不到命令、视频编解码器或系统动态库。
- `av`（PyAV）是 Python 包。版本与当前环境不一致时，可能在 `import av` 或 LeRobot 视频模块加载时出现导入错误、符号错误或编解码异常。

当前仓库的 `uv.lock` 锁定 `av==18.0.0`，当前固定的 LeRobot 版本要求 `av>=14.2.0`。已在当前 Python 3.11 环境确认 `av==18.0.0` 可以导入，且 `lerobot.common.datasets.video_utils` 可以正常加载。部署时不要再手工安装其他 PyAV 版本覆盖锁文件结果。

先检查当前环境，不要在检查命令中触发依赖更新：

```bash
ffmpeg -version | head -n 1

uv run --no-sync python -c "
import av
from lerobot.common.datasets import video_utils
print('PyAV:', av.__version__)
print('linked libav:', av.library_versions)
print('LeRobot video module: OK')
"
```

预期 PyAV 版本为 `18.0.0`。`av.library_versions` 显示的是 PyAV 实际链接的库版本，不要求与系统 `ffmpeg -version` 的版本号完全相同。

若系统 FFmpeg 缺失，执行：

```bash
sudo apt-get update
sudo apt-get install -y ffmpeg
```

若 PyAV 版本不是锁文件中的版本，或 `import av` 报错，应在仓库根目录重装锁定版本：

```bash
cd /home/user/Dobot/X-Trainer-Pi05-mydev
source .venv/bin/activate
uv sync --frozen --reinstall-package av
```

然后重新执行上面的 FFmpeg、PyAV 和 LeRobot 检查。不要通过修改 `LD_LIBRARY_PATH` 混用其他 Conda/系统环境中的 `libav*.so`；这容易再次造成 PyAV 与动态库不匹配。

### 4.4 RTC 参数和当前实机取值

异步 RTC 使用独立 worker 执行网络推理。机器人等待新 action chunk 时继续执行当前 chunk，并把旧 chunk 的剩余前缀发送给服务端，指导新 chunk 生成，以减少远程推理等待和动作切换突变。

| 参数 | 实机取值 | 作用 |
| --- | ---: | --- |
| `control_hz` | 22 | 客户端控制频率，与训练数据频率保持一致 |
| `action_horizon` | 25 | 每 25 个控制步发起下一次请求 |
| `rtc_inference_delay` | 6 | RTC 生成时采用的预计推理延迟步数 |
| `rtc_execution_horizon` | 15 | RTC 前缀过渡区域的结束位置 |
| `rtc_prefix_attention_schedule` | `linear` | 前缀注意力按位置线性变化 |
| `rtc_max_guidance_weight` | 10.0 | RTC 去噪引导最大权重 |
| `max_inference_delay_steps` | 24 | 在线结果允许的最大延迟步数 |
| `inference_timeout_s` | 3.0 | 在线请求网络超时 |
| `warmup_timeout_s` | 600 | 首次 JAX 编译和预热允许的超时 |
| `image_transport_codec` | `jpeg` | 使用 JPEG 减少网络传输量 |
| `image_jpeg_quality` | 90 | JPEG 质量 |

当前代码会检查：

```text
rtc_inference_delay >= 0
rtc_execution_horizon > 0
rtc_inference_delay <= rtc_execution_horizon
rtc_inference_delay < action_horizon
rtc_max_guidance_weight > 0
1 <= image_jpeg_quality <= 100
action_horizon + max_inference_delay_steps <= model_action_horizon
```

当前配置的模型 action horizon 为 50，实机参数满足 `25 + 24 = 49 <= 50`。旧文档中的 `max_inference_delay_steps=12` 和默认 `warmup_timeout_s=180` 与 9.9 实机命令不一致，本流程采用实际运行过的 24 和 600。

`linear` 是本次实机记录使用的 schedule。当前代码还支持 `exp`、`ones` 和 `zeros`，但这些值不属于本文已验证命令，不在部署流程中展开。

### 4.5 启动成功与兼容性判断

客户端连接后、控制机械臂前会验证服务端 metadata：

- `robot_side` 必须为 `right`；
- `physical_action_dim` 必须为 7；
- 模型动作槽位必须为 `[7:14]`；
- 相机键必须为 Top 和 Right wrist；
- reset pose 必须为 7 维；
- 协议必须为 `openpi-async-rtc` version 2；
- 服务端必须声明支持 RTC；
- 模型 action horizon 必须容纳当前请求间隔和最大延迟。

客户端完成 baseline warmup 和 RTC warmup 后才开始输出控制动作。任何 metadata 或动作维度检查失败都应停止运行，重新核对代码版本、config、checkpoint 和 norm stats，不能跳过检查。

开启 `--debug-async-timing` 后，日志会记录 request ID、round-trip latency、实际延迟步数、chunk 切换位置、服务端推理耗时和 JPEG 压缩统计，可用于判断网络或推理延迟是否超过设置。

### 4.6 安全停止与运行记录

- 终端使用 `Ctrl+C` 请求停止。
- 若开启相机预览，可按 `Q`、`Esc` 或关闭窗口停止。
- 出现方向异常、突然加速或即将碰撞时，优先触发机械臂急停，不要等待程序退出。
- `Ctrl+C` 后出现 `CancelledError` 或 `KeyboardInterrupt`，且此前服务已正常关闭时，通常只是人工中断日志。

客户端默认把推理动作保存到 `output/<timestamp>/`，包括收到的 action chunk、逐步选择动作、请求与延迟信息、CSV、NPZ、摘要和曲线。终端日志由命令中的 `tee` 单独保存。
